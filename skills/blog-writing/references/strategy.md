# 选题策略与传播机制

选题决定传播上限。再好的文笔也救不了一个没人关心的选题。

## 选题策略：写什么比怎么写更重要

### 四种选题来源

| 来源 | 原理 | 示例 | 传播力 |
|------|------|------|--------|
| **痛点挖掘** | 自己踩过的坑，读者也在踩 | "Spring Security 抽 Starter 时 import 焊死了" | 高（共鸣最强） |
| **版本里程碑** | 新版本发布窗口，搜索量集中爆发 | "Spring Boot 4 配置导入机制实测" | 高（时效性强） |
| **趋势借势** | 热门话题的延伸，蹭流量但不蹭热度 | "Rust 写后端是什么体验——Axum 权限系统实战" | 中高 |
| **竞品对比** | 选型决策类内容，读者收藏率最高 | "RuoYi vs youlai-boot：后台脚手架横评" | 高（收藏率高） |

> 痛点挖掘是最可靠的来源。你踩过的坑，一定有别人正在踩。把踩坑过程完整记录下来，比任何精心策划的选题都真实。

### 选题验证：三个问题

动笔前问自己：

1. **这个问题有没有 100 人在搜？** —— 没人搜的选题写得再好也没流量。去 CSDN、掘金搜关键词，看同类文章的阅读量
2. **读者看完能立刻用吗？** —— 能用的文章收藏率高，不能用的文章看完就关。收藏率是算法推荐的核心指标
3. **我有没有独特视角？** —— 如果网上已有 10 篇类似文章，你的那篇凭什么被看？要么更深入，要么有不同观点

三个问题都"是"，写。有一个"否"，换选题或调整角度。

### 选题公式

**公式**：`[技术栈] + [动词] + [场景/结果]`

| 公式 | 示例 |
|------|------|
| 框架 + 搭建 + 场景 | Spring Boot + 搭建 + 多租户 SaaS 系统 |
| 框架 + 升级 + 结果 | Vite 7 + 升级 + 构建提速 50% |
| 框架 + 对比 + 决策 | Spring Security vs Sa-Token + 权限方案选型 |
| 问题 + 解决 + 方案 | JWT 无法踢人 + 解决 + Redis 双会话方案 |

> 避免"浅析""探究"这类学术词。技术博客读者要的是"能不能用"，不是"理论分析"。

## 爆火机制：让文章被转发收藏

"写得好"和"被转发"是两件事。好文章被埋没，通常缺的不是质量，而是传播触发点。

### 爆火公式

**爆火 = 情绪触发 × 社交货币 × 实用价值**

三个要素缺一不可。只有情绪没有实用价值，是标题党；只有实用价值没有情绪，是工具书——工具书不会被转发，只会被收藏然后遗忘。

### 四个情绪触发器

| 触发器 | 原理 | 写法 | 示例 |
|--------|------|------|------|
| **共鸣** | "对，我也遇到过！" | 描述读者经历过的真实痛点 | "你接过半年前的项目，打开代码——userId、user_id、uid 三种命名并存" |
| **意外** | "原来如此！" | 打破常识认知 | "大多数人以为安全框架和业务耦合是正常的——一行 import 就焊死了" |
| **焦虑** | "我是不是也踩了这个坑？" | 揭示常见但被忽视的问题 | "你的 SysUserDetailsService 里那行 import，正在阻止你抽出 Starter" |
| **爽感** | "这也太方便了！" | 展示量化收益或一键解决 | "3 分钟跑通，本地不装 MySQL 也能调试" |

> 一篇文章至少触发一个情绪。没有情绪的文章，读者看完的反应是"哦"——"哦"不会触发转发。

### 社交货币：让读者愿意转发

读者转发一篇文章，本质上是在说"看这篇文章的我，很厉害"。所以文章要能给读者提供社交价值：

- **谈资**：文章里有别人不知道的信息（"9 套后端共享同一套 API"）
- **观点**：文章里有明确判断，读者可以引用（"90% 的 SaaS 第一阶段不需要独立数据库"）
- **工具**：文章可以当参考收藏，转发等于"我在用这个"（技术栈对比表、检查清单）

> 没有观点的文章不会被转发。"各有优劣"不是观点，是废话。

### 争议性观点的边界

有争议才有讨论，有讨论才有传播。但争议不等于引战——**对事不对人，有观点但有依据**。

| 可以做 | 不要做 |
|--------|--------|
| "我不推荐用 Sa-Token 替代 Spring Security，理由是..." | "Sa-Token 就是垃圾" |
| "90% 的 SaaS 不需要独立数据库" | "用独立数据库的都是菜鸟" |
| 给出具体代码证据支撑观点 | 只下结论不给理由 |

> 争议性观点放在文章中段，不要放标题。标题引战会被平台限流。

### 时效性窗口

新版本发布、重大技术事件后 72 小时是黄金窗口。这时候搜索量暴增，但优质内容还没出来。

| 时机 | 动作 | 效果 |
|------|------|------|
| 版本发布前（RC 阶段） | 提前写好升级指南，发布日当天发 | 抢占搜索第一批结果 |
| 发布后 24 小时内 | 发"实测体验"类文章 | 算法推荐权重最高 |
| 发布后 3-7 天 | 发"踩坑总结"类文章 | 竞品内容开始泛滥，差异化突围 |

> 错过窗口不是不写，而是换角度——从"新功能介绍"转为"踩坑总结"或"深度源码解析"。

## 叙事弧：用故事结构留住读者

效果前置解决"开头看不看"的问题，叙事弧解决"中间走不走"的问题。读者中途流失，往往是因为文章是"功能清单"而不是"故事"。

### 四步叙事弧

```
问题（读者认出痛点）
  → 挣扎（试过的方案为什么不行）
    → 顿悟（原来问题出在这里）
      → 方案（本文的解法 + 效果验证）
```

这不是编故事，是把真实的技术决策过程还原出来。读者跟着走一遍，理解比看说明书深 10 倍。

### 叙事弧与效果前置的关系

效果前置是"把结果提前剧透"，叙事弧是"把过程讲出来"。两者不矛盾：

```markdown
## 效果 PK：方案 A vs 方案 B
（结果前置——让读者知道看完能得到什么）

---

## 正文

### 问题：为什么 99% 的项目做不到安全内核独立
（叙事弧第一步——痛点共鸣）

### 挣扎：直接抽接口为什么不行
（叙事弧第二步——展示试错过程）

### 顿悟：一行 import 就是问题根源
（叙事弧第三步——恍然大悟时刻）

### 方案：端口-适配器解耦
（叙事弧第四步——本文解法）
```

> 效果前置给读者"值得看"的理由，叙事弧给读者"继续看"的动力。两者配合，开头和中段都不丢人。

### "恍然大悟"段落公式

叙事弧的第三步（顿悟）是全文最关键的段落——这是读者收藏转发的触发点。

**四步公式**：

```
1. 普遍认知：大多数人以为 {常见做法/误区}
2. 真实原因：其实是 {根本原因}
3. 代价揭示：结果就是 {负面后果}
4. 本项目解法：{方案} 解决了这个问题——{效果}
```

**示例**：

> 大多数人以为安全框架和业务代码耦合是正常的——反正能跑。其实一行 `import` 就把安全内核焊死在了业务模块上。结果就是：换业务实现要改安全代码，抽 Starter 复用要先拆依赖。youlai-boot 用端口-适配器模式解决了这个问题——安全内核只定义接口，业务模块提供实现，两者编译期互不依赖。

> 第一步要戳中读者的真实经验（"对，我项目就是这样"），第四步要给出可验证的代码证据（不是空谈"我们设计得很好"）。
