# 分类目录参考

按文章的主要任务选择一种类型，以对应目录起草，替换技术对象和业务动作。示例不是必填章节：内容较少时合并，缺少实质内容时删除，不拼接多套完整目录。

## 类型选择

| 类型 | 主要任务 |
|---|---|
| 技术整合 | 给现有项目接入框架、中间件或服务，并用小案例验证。 |
| 环境部署 | 把应用部署起来，让读者能访问并检查结果。 |
| 功能开发 | 从需求、数据到前后端联调，完成一个可使用的功能。 |
| 原理解析 | 解释机制、调用流程或设计选择，形成可迁移的理解。 |
| 问题排查 | 根据实际证据解释故障，展示定位、修复和验证。 |
| 技术选型 | 在明确约束下比较方案，给出可执行的选择建议。 |
| 项目介绍 | 帮读者判断项目是否适合自己，并能试用和理解核心设计。 |

问题排查不作为功能实战的默认结构。

## 使用约定

- 全文一个 H1，正文用 H2，需要拆解不同任务或机制时再用 H3；不跳级，不为短文凑层级。
- 标题默认不编号；用户明确要求或原稿、发布模板已有编号时按其格式。顺序操作用有序列表；平台自动编号不重复手写，目录与正文标题一致。
- 同级标题简短，长度接近、粒度一致、表达协调；下级只拆解所属父节。保留必要术语，条件与结论放在正文，不为严格等字数凑词，也不用“实例一、实例二”代替内容。
- 按阅读依赖安排顺序：准备在使用之前，配置在验证之前。目录优先表达任务、对象或机制，文件路径和实现细节放在代码旁。
- 下列示例只列正文目录。“前言、总结、常见问题、进阶”等仅在有独立信息时设节，不重复正文，不为每个步骤套同一组小标题。

## 技术整合

适合把中间件或框架接入现有项目。下面以 Redis 缓存为例，沿“了解用途—完成接入—使用缓存—确认结果”展开。

```markdown
## 技术概览
### 核心能力
### 适用场景

## 环境搭建
### 服务安装
### 项目依赖

## 基础配置
### 连接配置
### 序列化配置

## 实战应用
### 缓存查询
### 缓存更新

## 接入验证
### 结果检查
### 失效验证
```

概览只讲本次接入需要的能力，读者已有基础时可压缩。读取、更新和失效围绕同一数据对象展开，不扩成技术百科。

## 环境部署

适合把前后端应用部署为可访问的服务。下面以 Docker Compose 为例，先确定访问入口和服务关系，再落到构建、编排与检查。

```markdown
## 环境准备
### 环境要求
### 工具安装

## 项目打包
### 后端构建
### 前端构建

## 服务编排
### 服务配置
### 代理配置
### 数据目录

## 运行配置
### 证书配置
### 日志配置

## 部署验证
### 启动服务
### 访问检查
```

证书、日志等配置按部署目标取舍。验证沿实际访问链路检查，不能仅凭进程启动判断页面和接口可用。

```markdown

### 功能范围
### 操作流程

## 数据设计
### 数据结构
### 接口约定

## 后端实现
### 文件上传
### 商品保存
### 详情查询

## 前端实现
### 页面布局
### 上传交互
### 编辑回显

## 功能验证
### 正常流程
### 关键分支
```

按业务任务串起数据、接口与页面，已有结构不另造新表。小功能可合并前后端章节，沿一次用户操作讲清改动。

验证覆盖上传、随商品保存、重新打开后回显；替换、清空等在承诺范围内再检查。

## 原理解析

适合解释机制、调用流程和设计取舍。下面以线程池任务执行为例，从可观察行为进入，再走过内部过程。

```markdown
## 问题引入
### 行为示例
### 核心疑问

## 整体流程
### 核心对象
### 执行过程

## 机制解析
### 任务提交
### 线程调度
### 结果处理

## 设计取舍
### 队列选择
### 拒绝策略
```

用同一输入跟踪对象和状态变化，再说明机制对开发选择的影响。涉及源码时注明版本、路径和关键符号；只讲机制时不承诺逐行源码分析。

## 问题排查

适合用户明确要求的排错教程、故障分析或复盘。按证据组织，保留影响判断的环境、版本和配置。

```markdown
## 问题现象
### 异常表现
### 复现条件

## 排查过程
### 证据收集
### 假设验证

## 根因分析
### 触发条件
### 影响机制

## 修复方案
### 处理措施
### 关键改动

## 结果验证
### 复现回测
### 复发预防
```

按“证据支持什么判断”组织排查，不编造失败尝试。错误信息保留可搜索的原文，修复后按原触发条件回测；区分临时缓解与根因修复，预防措施有具体内容再保留。

## 技术选型

适合在明确约束下比较方案。开头先给推荐及成立条件，正文展开依据；下面以本地缓存与 Redis 缓存为例。

```markdown
## 需求约束
### 核心需求
### 实际限制

## 候选方案
### 本地缓存
### Redis 缓存

## 方案对比
### 一致性要求
### 访问延迟
### 维护成本

## 选型建议
### 推荐方案
### 适用边界
### 接入成本
```

在同一任务、同一条件下比较。表格列差异，正文解释决定选择的原因与适用边界，并说明条件变化后怎样改选，不以“各有优劣，按需选择”结束。

## 项目介绍

适合介绍开源项目，帮助读者判断、试用和理解。下面以后台管理项目为例。

```markdown
## 项目简介
### 项目定位
### 适用场景

## 功能概览

## 快速开始
### 环境要求
### 本地启动

## 项目结构

## 核心设计
### 菜单生成
### 路由注册
### 权限校验
```

开头给可用的体验入口、源码地址或代表性效果。功能概览支持项目定位，项目结构只解释后文要用的目录；核心设计沿一次操作或调用深入，避免照搬 README 或堆砌功能、技术栈。

## 目录复核

单独扫读目录，检查能否看出文章主线、先后是否衔接、同级是否协调、父子是否相属。删除重复或空泛的节；采用编号时检查连续性。
