# 类型、测试、注释与交付

## TypeScript 质量

- 沿用仓库当前 `strict` 设置；新增代码不扩大 `any`、非空断言和无校验类型断言。
- 第三方数据、缓存内容、环境变量和反序列化结果位于信任边界，先校验再转换为内部类型。
- 使用 `unknown` 接收未知异常或外部值，并通过类型缩小处理。
- 注入成员使用 `private readonly redisService` 这类普通 camelCase；TypeScript 的访问修饰符已经表达私有性，不加 `_` 前缀。
- `await` 的保留应有语义，例如位于 `try/catch` 中以便捕获异步异常；不要机械添加或删除。
- 不通过 `as any`、`eslint-disable`、降低 strictness 或删除失败断言来让检查变绿。

## 测试策略

根据风险选择最小充分组合：

| 改动 | 重点验证 |
| --- | --- |
| 纯函数、mapper、policy | 单元测试边界值和错误分支 |
| Service 用例 | mock 或测试数据库验证依赖交互、事务和权限范围 |
| Controller / DTO | 请求转换、校验、状态码和响应 schema |
| Guard / decorator | 无元数据、允许、拒绝、超级管理员和数据范围 |
| Repository / 复杂查询 | 真实数据库集成测试，覆盖分页、排序、软删除和并发 |
| 登录、权限、文件等关键流程 | e2e 测试正常路径及安全失败路径 |
| 配置或 bootstrap | 启动 smoke test 与 e2e bootstrap 一致性 |

e2e 应尽量复用生产 bootstrap 的关键配置：全局前缀、版本、ValidationPipe、Filter、Interceptor 和 Guard。若测试刻意省略某项，应明确原因，否则测试通过不代表真实应用契约正确。

修复缺陷时先写能复现问题的测试，再实施修复；若基础设施导致测试无法运行，记录它属于本次引入还是仓库基线问题。

## 验证顺序

先从 `package.json` 读取真实脚本，使用仓库锁文件对应的包管理器。常见顺序是：

1. 目标模块或文件的聚焦测试。
2. TypeScript typecheck 或 Nest build。
3. lint 与格式检查。
4. 受影响模块的单元或集成测试。
5. 相关 e2e；安全、持久化或全局 bootstrap 改动提高覆盖范围。

不要假设脚本一定叫 `test`、`lint` 或 `build`。也不要执行会自动改写大量无关文件的全库 `lint --fix`，除非用户明确要求。

最终报告区分：

- 本次改动导致的失败。
- 修改前已经存在的基线失败。
- 因环境、服务或凭据缺失而未运行的检查。
- 尚需人工验证的行为。

## 注释原则

值得写注释的内容：

- 业务规则背后的原因和不变量。
- 安全敏感的默认行为与威胁假设。
- 事务边界、并发方案和提交后副作用。
- 外部系统兼容、临时迁移约束和非显然性能权衡。
- 导出给其他模块或包使用的稳定契约。

不值得写的内容：

- 对代码逐句翻译，如 `// 查询用户` 紧邻 `findUser()`。
- 类型已经完整表达的 `@param id 用户 ID`、`@returns 返回结果`。
- 容易过期的实现步骤或作者、日期信息。
- 注释掉的旧代码；应删除并依赖版本控制。

示例：

```typescript
/**
 * 在同一事务内替换角色权限，避免读者观察到部分更新状态。
 * 权限缓存必须在事务提交后失效。
 */
async replacePermissions(roleId: string, permissionIds: string[]): Promise<void> {
  // ...
}
```

这里的注释补充了事务不变量和副作用时机，而不是复述方法名。

## DTO 和 API 文档

- `class-validator` 描述运行时约束，OpenAPI decorator 描述对外 schema；两者应一致。
- `description` 解释业务含义，避免只把属性名翻译成中文。
- 枚举、可空性、默认值、示例和数组元素类型与真实验证保持一致。
- 敏感请求示例不得包含可用密钥、真实手机号、令牌或密码。
- 若项目不使用 Swagger，不要为了本 Skill 强制引入；改用现有 schema 或 API 文档机制。

## 评审清单

- 是否误改了用户已有变更或无关文件？
- 请求、内部模型、Entity 和响应是否边界清晰？
- 是否存在未使用依赖、循环依赖或过度导出？
- HTTP 状态、错误结构和日志是否既可诊断又不泄密？
- 多写操作是否原子，提交后副作用是否可能提前发生？
- 测试是否覆盖新增行为的失败路径和权限边界？
- 注释是否解释了代码本身无法表达的信息？
- 最终交付是否列出已执行验证与剩余风险？
